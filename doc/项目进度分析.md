## 二、方案文档实现状态（WebRTC网盘与分享方案.md §8）

文档第八章「文件分享模块设计」与当前服务端对比如下。

### 2.1 文档设计要点

- **服务端无分享记录**：分享记录存在 Desktop/客户端本地，服务端只维护「设备在线状态 + 信令转发」。
- **分享链接**：`/share/{deviceId}/{shareCode}`，由服务端提供**通用分享页**（静态/模板）。
- **单一 WebSocket**：设备注册 + 浏览器「连接某设备」+ offer/answer/ice 转发，都在同一套 WS 上（文档写的是 `/api/connect`，实际可对应到当前 `/api/share` 的扩展）。

### 2.2 当前 fast_send_server 已实现

| 能力 | 状态 | 说明 |
|------|------|------|
| 设备上线/离线 | ✅ 已实现 | `/api/share` WS：`device-online`、`device-online-ack`、心跳、超时清理 |
| 设备状态存储 | ✅ 已实现 | `devices` Map、`socketDeviceId`，内存 |
| 取件码信令（send/receive） | ✅ 已实现 | `/api/connect` WS：send/receive/code、sdp/candidate 转发 |
| 分享 REST API | ⚠️ 与文档不一致 | 有：POST/GET/DELETE `/api/share`，分享记录存在**服务端内存** |
| 分享页路由 | ❌ 未实现 | 文档要求 `/share/[deviceId]/[code]` 通用页面，当前无此路由 |
| 浏览器「连接设备」流 | ❌ 未实现 | 文档：浏览器发 `connect` + deviceId → 服务端返回 device-online 或 OFFLINE，并转发 offer/answer/ice |
| WebRTC 信令在 share 路径的转发 | ⚠️ 部分 | 仅 `peer-connect` 转发到设备，缺少浏览器侧 connect + offer/answer/ice 的完整双向转发 |

### 2.3 文档 §8.10 实现步骤与当前对应

| 步骤 | 文档描述 | 当前状态 |
|------|----------|----------|
| 阶段一：服务端扩展 | 扩展 WS：设备上线/离线、分享请求转发、WebRTC 信令转发；deviceStore；分享下载页 `/share/[deviceId]/[code]` | 设备上下线 ✅；分享请求与浏览器↔设备信令转发 ❌；分享页 ❌ |
| 阶段二：Desktop 端 | device-manager、本地分享码与链接、处理分享请求与 WebRTC | 依赖服务端先补齐（见下） |
| 阶段三 | 删除本地 HTTP 分享服务、简化分享对话框 | 文档标为已完成 ✅（针对当时 Electron 方案） |

## 三、当前进度结论

### 3.1 文档层面

- **已完成**：迁移方案、WebRTC 网盘/分享方案两篇总览文档。  
- **未完成**：P0 的五篇文档（架构、信令协议、API/分享、数据模型、Flutter 联调）**全部未写**。  
- **推荐下一步（文档）**：按计划顺序先写 **`服务端架构总览.md`**；**`信令协议说明.md`** 已完成。后续补 分享接口说明、数据模型设计、Flutter 联调计划 等文档。

### 3.2 服务端层面（相对 webrtc-cloud-storage-solution §8）

- **已具备**：  
  - 双 WS：`/api/connect`（取件码 + sdp/candidate）、`/api/share`（设备注册 + 心跳 + peer-connect 转发）。  
  - 设备在线状态（内存）。  
  - 分享的 REST 增删查（与文档「分享仅存 Desktop」不一致）。  
- **缺且影响「按文档正常运行」的**：  
  1. **分享页**：`/share/{deviceId}/{shareCode}` 的页面或路由（文档要求通用下载页）。  
  2. **浏览器侧「连接设备」流程**：浏览器连 WS → 发 `connect` + deviceId → 服务端判断设备在线 → 返回 `device-online` 或 `error OFFLINE`，并在此连接上转发 offer/answer/ice（与现有 Desktop 的 offer/ice 配对）。  
  3. **协议与文档统一**：若严格按 §8，需在文档与实现二选一：  
     - **方案 A**：服务端去掉分享存储，只做设备状态 + 信令转发；分享创建/列表/删除全部在 Desktop；API 仅保留「分享页」所需（若有）。  
     - **方案 B**：保留当前服务端存分享的 REST 设计，在文档中改写 §8，明确「服务端可选的分享存储」与「分享页 + 浏览器连接设备 + 信令转发」的关系。

## 四、后续建议：先做哪一项才能「文档 + 服务端」都闭环

### 4.1 若目标：严格按现有 webrtc 文档跑通

建议顺序：

1. **先定协议并落文档（优先）**  
   - **`信令协议说明.md`** 已落稿；后续实现时以该文档为准：  
     - 明确两条 WS：`/api/connect`（取件码）、`/api/share`（设备 + 浏览器连设备 + 信令转发）。  
     - 定义「浏览器连接设备」消息：`connect`(deviceId)、服务端回复 `device-online` / `error OFFLINE`，以及 offer/answer/ice 在 share 上的转发格式。  
   - 这样服务端实现和 Flutter/Web 客户端才能对齐，避免返工。

2. **再补服务端能力**  
   - 在 **`/api/share`** 上实现：  
     - 浏览器连接后发 `connect` + deviceId；  
     - 服务端查 `devices`，回 `device-online` 或 `error OFFLINE`；  
     - 同一连接上后续的 offer/answer/ice 在「该浏览器 ↔ 对应 device 的 WS」之间双向转发（可与现有 `peer-connect` 扩展或合并）。  
   - 增加 **分享页**：`GET /share/:deviceId/:shareCode` 返回静态页或模板（内容可为通用下载页，具体逻辑由前端 + WS 完成）。

3. **然后写其余 P0 文档**  
   - `服务端架构总览.md`：当前 Nest 模块（Signaling + Share）、双 WS、设备/会话状态。
   - `分享接口说明.md`：若采用方案 A，重点写「无服务端分享存储」+ 分享页 + WS 行为；若方案 B，写当前 REST + 与分享页/WS 的分工。
   - `数据模型设计.md`：devices（内存）、sessions（取件码会话）、以及是否保留 shares（若方案 B）。
   - `Flutter与服务端联调计划.md`：baseUrl、WS 地址（connect/share）、鉴权、错误码、重连。

### 4.2 若目标：先让服务端能「跑起来」再慢慢对齐文档

- 当前服务端已能运行：  
  - 取件码流程：`/api/connect` 可用。  
  - 设备注册：Desktop 连 `/api/share` 可上线、心跳、收 `peer-connect`。  
- 要「按文档完整跑通分享流程」，仍需补齐上面 **4.1 的 2**（浏览器 connect + 信令转发 + 分享页）。  
- **`信令协议说明.md`** 已写好，后续改代码时以该文档为准，保持实现与协议一致。
