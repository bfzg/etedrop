# 信令协议说明

## 一、背景与目标

FastSend 服务端提供两条 WebSocket 信令通道：

1. **取件码通道**（`/api/connect`）：发送方生成取件码，接收方凭码加入会话，用于「传文件」场景的 WebRTC 信令交换。
2. **分享/设备通道**（`/api/share`）：Desktop 设备注册上线、心跳保活；后续可扩展为浏览器通过 deviceId 连接设备并交换 WebRTC 信令（分享下载场景）。

本文档约定两条通道的消息类型、方向、载荷格式及状态机，便于客户端与服务端对齐实现。

---

## 二、范围

| In Scope | Out of Scope |
|----------|--------------|
| WebSocket 消息类型、字段、方向 | HTTP REST API |
| 取件码会话生命周期与转发规则 | WebRTC SDP/ICE 具体格式（仅约定透传） |
| 设备上线/离线、心跳、超时 | P2P DataChannel 内业务协议（分享请求、文件块等） |
| 错误码与常见错误消息 | 鉴权、JWT（当前版本未实现） |

---

## 三、通用约定

- **传输格式**：所有消息为 JSON 对象，UTF-8 编码。
- **必填字段**：每条消息至少包含 `type: string`，表示消息类型。
- **扩展字段**：除 `type` 外，各消息可携带其它字段（如 `code`、`data`、`msg` 等），见下文。
- **连接**：客户端通过 `ws://host/api/connect` 或 `ws://host/api/share` 建立连接，服务端不要求 URL 查询参数；同一连接上可连续发送多条消息。

---

## 四、取件码通道（/api/connect）

用于「发送方—服务端—接收方」的取件码会话：发送方先发 `send` 获得取件码，接收方发 `receive` 带取件码加入，之后双方通过服务端转发 `sdp` / `candidate` 建立 WebRTC 连接。

### 4.1 客户端 → 服务端

| type | 说明 | 其它字段 |
|------|------|----------|
| `send` | 发送方发起，请求生成取件码 | 无 |
| `receive` | 接收方发起，凭取件码加入会话 | `code: string`（取件码，大小写不敏感，前后空格忽略） |
| `sdp` | WebRTC SDP（offer/answer） | `data: object`（透传至对端） |
| `candidate` | WebRTC ICE candidate | `data: object`（透传至对端） |
| `ping` / `heartbeat` | 保活或探测 | 无 |

### 4.2 服务端 → 客户端

| type | 说明 | 其它字段 |
|------|------|----------|
| `code` | 取件码已生成（仅发给发送方） | `code: string` |
| `status` | 接收方加入结果 | `code: number`（0 成功，404 取件码无效或发送方未在） |
| `peer-connect` | 接收方已加入（仅发给发送方） | `code: string`（取件码） |
| `sdp` / `candidate` | 来自对端的 WebRTC 信令 | `data: object` |
| `ping` | 心跳回应 | 无 |
| `err` | 错误 | `msg: string` |

### 4.3 取件码会话状态与规则

- 发送方发 `send` 后进入会话，获得唯一取件码；同一连接上重复发 `send` 会先清理旧会话再生成新码。
- 接收方发 `receive` 且 `code` 有效时，与发送方配对；同一取件码仅允许一名接收方，后续接收方收 `err`（如「该取件码已被使用」）。
- 配对成功后，双方可互发 `sdp`、`candidate`，服务端按会话关系转发给对端；未配对或会话不存在时发 `sdp`/`candidate` 会收 `err`。
- 任一方断开或超时未使用，会话被清理；对端收到 `err`（如「发送方已断开连接」「接收方已断开连接」「会话已超时」）。

### 4.4 取件码时序（简图）

```
发送方                    服务端                    接收方
  |                         |                         |
  |-------- send ---------->|                         |
  |<------- code -----------|                         |
  |                         |                         |
  |                     [接收方输入取件码]             |
  |                         |<-------- receive -------|
  |                         |-------- status ------->|  (code: 0)
  |<------- peer-connect ----|                         |
  |                         |                         |
  |-------- sdp ---------->|-------- sdp ---------->|
  |<------- sdp ------------|-------- sdp -----------|
  |-------- candidate ----->|-------- candidate ----->|
  |<------- candidate ------|-------- candidate ------|
  |         ... WebRTC 建立 ...                        |
```

## 五、分享/设备通道（/api/share）

用于 Desktop 设备注册与保活；当前实现仅包含设备侧，浏览器侧「连接设备」及 offer/answer/ice 转发为规划能力，在本文档中一并约定，便于后续实现。

### 5.1 Desktop → 服务端

| type | 说明 | 其它字段 |
|------|------|----------|
| `device-online` | 设备上线注册 | `deviceId: string`（必填）, `deviceName?: string` |
| `heartbeat` / `ping` | 心跳 | 无 |
| `peer-connect` | （规划）将浏览器侧的连接请求或信令转发给服务端，由服务端转发给对应设备 | `deviceId: string`, `data?: object` |

### 5.2 服务端 → Desktop

| type | 说明 | 其它字段 |
|------|------|----------|
| `device-online-ack` | 上线成功 | `deviceId: string`, `serverTime?: number` |
| `peer-connect` | （规划）浏览器请求连接该设备或 WebRTC 信令 | `data: object` |
| `ping` | 服务端心跳 | 无 |
| `err` | 错误 | `msg: string`（如 deviceId 为空、设备尚未注册等） |

### 5.3 设备注册与心跳规则

- 设备必须先发 `device-online` 且 `deviceId` 非空，才视为已注册；之后可发 `heartbeat`/`ping` 保活。
- 同一 `deviceId` 若再次从新连接注册，旧连接会被服务端关闭，新连接取代。
- 服务端定期清理超时未心跳的设备（具体超时时间见服务端配置），并关闭对应 WebSocket。

### 5.4 浏览器侧（规划）

以下为文档与方案设计中约定的能力，当前服务端尚未实现，列在此处便于后续开发对齐：

- 浏览器连接同一 `/api/share`（或单独端点），首条消息为 `connect`，携带 `deviceId`。
- 服务端根据 deviceId 查设备是否在线：
  - 在线：回复 `device-online`（或等价），并在此后的同一条连接上，在「浏览器 ↔ 该设备」之间双向转发 `offer` / `answer` / `ice-candidate`。
  - 离线：回复 `error`，`code: 'OFFLINE'`，`message` 如「分享者设备离线」。

实现时可在本文档中补充「浏览器 ↔ 服务端」的完整消息表与时序图。

## 六、错误与边界处理

- **消息格式错误**：非 JSON 或缺少 `type` 时，服务端可关闭连接或回复 `err`，`msg` 如「消息格式错误」。
- **不支持的消息类型**：服务端回复 `err`，`msg` 如「不支持的消息类型: xxx」。
- **取件码**：无效或已使用时报 `status code: 404` 或 `err`；会话超时、对端断开时统一用 `err` + `msg` 说明原因。
- **设备**：未注册就发心跳收 `err`「设备尚未注册」；`deviceId` 为空收 `err`「deviceId 不能为空」。

---

## 七、验收标准

- 客户端能通过 `/api/connect` 完成「发送方取码 → 接收方填码 → 双方交换 sdp/candidate」的流程，并成功建立 WebRTC 连接。
- Desktop 能通过 `/api/share` 完成设备上线、心跳，并收到 `device-online-ack`；超时未心跳时被服务端踢下线。
- 所有约定消息类型在实现中有对应处理；未约定类型收到 `err` 提示。

---

## 八、待办项与风险

| 待办 | 说明 |
|------|------|
| 浏览器连接设备流程 | 在 `/api/share`（或新路径）上实现 `connect` + deviceId 与 offer/answer/ice 双向转发 |
| 错误码统一 | 将 `err.msg` 与 HTTP 风格错误码做统一规范（可参考后续《错误码规范》文档） |
| 鉴权 | 当前无鉴权；若后续加 JWT 或设备签名，需在握手或首包中约定 |

**风险**：协议与实现不一致时，客户端会连不通或行为异常；任何新增消息类型或字段应在本文档中补充后再实现。
